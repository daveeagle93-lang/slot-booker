# Known limits

Things the app does not do, or does less well than you might expect. Admin sign-in has its own list in [admin-auth.md](admin-auth.md#known-limits), and the settings page has one in [branding.md](branding.md#known-limits).

- **The admin event list builds each upcoming event's schedule in the Worker.** Measured in Node on a dev machine (not in workerd), a 500-slot event costs about 0.45 ms, so a list with around 20 events of that size could exceed the Free plan's 10 ms CPU limit. Typical events (about 30 slots) cost well under 1 ms each. Storing the slot count would remove the cost if it ever matters.
- **Booked counts and the Full badge count every booking row.** Bookings on slots that are no longer in the schedule (orphans) should no longer be creatable now that edits, swaps and public bookings are guarded, but legacy data could contain them, and they would be counted.
- **Archived events are not included in the Past bulk clear-out.** They can be deleted one at a time, and nothing reminds anyone to, so organisers should delete archived events they no longer need.
- **Names and club text refuse every Unicode format character** (category Cf), which includes the invisible joiners that emoji sequences and some scripts use. Plain emoji and accented names are fine. A value in the booking form must also contain at least one letter or number (so a value of only an emoji is refused; "Rex 🐶" is fine), and invisible characters such as variation selectors and Hangul fillers are ignored when deciding whether two bookings have the same identity (the same values in the fields that identify a booking).
- **The app does not stop one person taking two places at the same time.** With an identity limit above 1 the same identity (the same values in the fields that identify a booking) may hold several bookings at once, including two places at the same time (another lane, or another place in the same lane). The limit counts bookings, not times. Lowering the limit below what an identity already holds keeps its bookings; it just can't book again until it holds fewer than the limit.
- **A big edit save passed on a real Workers Free account; a badly contended booking is still unchecked.** I measured how many SQL statements the Worker sends (counting each statement of a batch, in `src/test/statement-counts.test.ts`, against the local database): a typical edit save (3 breaks, 3 lanes, 4 fields, capacity changed) sends 18, 12 of them in one batch; a worst-case one (20 breaks, every one of 10 lanes renamed and reordered, 4 fields changed, capacity lowered) sends 58, 51 of them in one batch; a public booking sends 10 on the happy path, 15 after losing a race for a place once, and 19 after an edit raced its insert once. A booking that keeps losing the race for a place retries up to capacity + identity limit + 2 times, about 5 statements each: 361 statements in 144 `batch()` calls at the extreme (capacity 50, identity limit 20, every attempt lost). Cloudflare's Workers Free plan allows 50 D1 queries per invocation, and its documentation does not say whether each statement of a `batch()` counts toward that. I checked the worst-case edit save on the preview deployment on 21 October 2026 (Wrangler 4.147): I seeded an event with 10 lanes, 3 fields, capacity 2 and 20 breaks, then saved an edit that replaced the 20 breaks, renamed and reordered all 10 lanes, changed the 4 fields and lowered capacity to 1. It sent 58 statements (51 of them in one `batch()`) and the Worker answered 200 OK, with every change saved and no exception in `npx wrangler tail --env preview`. The account is on the Workers Free plan (I inferred that from Cloudflare refusing to set `limits` on it, not from the dashboard), so a batch is not counted statement by statement against the limit of 50. Still unchecked: a booking that loses the race for a place again and again. At the extreme that is 144 `batch()` calls, more than 50 even if each batch counts once, and I could not provoke it on a deployed copy: it needs capacity 50, identity limit 20 and every insert lost. If a request did pass the limit, the app would answer 500 "Something went wrong. Please try again." (a booking is not made; an edit save is one batch, which is one transaction, so a failed save should write nothing, though I have not verified that for this kind of failure). If you ever see errors about too many queries or subrequests in `npx wrangler tail --env preview`, the batches can be split or the retry bound lowered; that has not been done.
- **There are no per-version preview URLs** (`preview_urls` is off in `wrangler.jsonc`): they would serve the whole app, admin included, on extra hostnames, and use the production database by default.
- **The booking API has no rate limiting or bot protection.** Only the admin sign-in and `/setup` count attempts. Add something like Cloudflare Turnstile before posting a link publicly.
